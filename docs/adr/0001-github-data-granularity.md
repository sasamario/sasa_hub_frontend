# ADR-0001: GitHub活動データは明細単位で保存し、集計は参照時に行う

- ステータス: 承認
- 日付: 2026-07-20
- 関連要件: F-01(GitHub連携), F-03(オンデマンド同期), F-11(活動の一覧表示)

## 背景

GitHubの活動データ(コミット・PR等)をDBにどの粒度で保存するかを決める必要がある。
利用者の当初の要望は「コミット数・PR数などの件数を集計できればよい」であり、
これを満たす方式として以下の2案が考えられた。

- A案: 1コミット・1PRを1レコードとして明細で保存し、件数は参照時に集計(COUNT)する
- B案: 日別・月別などにあらかじめ集計した件数のみを保存する

## 決定

**A案を採用する。** GitHubの活動は明細単位(1コミット/1PR = 1レコード)で保存し、
「コミット数」などの集計値は保存せず、ダッシュボード表示時にクエリで算出する。

いわゆる「生データは残し、集計は表示時に計算する」というデータ設計の定石に従う。
これにより、当初要望である「件数の集計」も問題なく満たせる。

## 理由

1. **オンデマンド同期との相性(重複防止・差分取得)**
   明細を保持すればコミットSHA等を一意キーとして「取り込み済みか」を判定でき、
   同期のたびの二重カウントや取りこぼしを防ぎやすい。B案は集計値同士の突き合わせが必要で
   実装が複雑になり、二重計上のリスクが高い。

2. **要件F-11(活動の一覧表示)を満たせる**
   時系列で「どのリポジトリに何をしたか」を一覧表示するには明細が必須。
   B案では数値しか残らず、この要件を満たせない。

3. **集計の柔軟性**
   明細さえあれば月別・週別・リポジトリ別など任意の切り口で後から集計できる。
   B案で特定粒度(例: 月別)で保存すると、後から別粒度(例: 週別)で見たくなっても
   元データがなく再構成できない。

## 検討した代替案

### B案: 集計値のみを保存

- 却下。上記1〜3の課題があるため。
- 「件数だけならシンプル」という見かけ上の利点はあるが、同期の堅牢性・要件充足・
  将来の拡張性のいずれの面でもA案に劣る。

## 影響

- ストレージ使用量は明細保存の分だけ増えるが、個人利用かつローカルPostgreSQLのため
  実用上問題にならない。
- 集計処理は参照時にクエリで行うため、集計ロジックはアプリ/クエリ側に持つ。
- この方針はGitHubに限らずQiita等の他ソースにも適用する(明細保存を基本とする)。
