# ADR-0002: GitHubはコミットとPRの両方を取得し、集計側で二重カウントを回避する

- ステータス: 承認
- 日付: 2026-07-20
- 関連要件: F-01(GitHub連携), F-03(オンデマンド同期), F-11(活動の一覧表示)
- 関連ADR: ADR-0001(明細を保存し集計は参照時に行う)

## 背景

GitHubの活動として何を取得・保存するかを決める必要があった。
コミットとPRは別概念であり(1つのPRは複数のコミットを内包する)、
両方を単純に合算すると同じ作業を二重にカウントしてしまう懸念がある。

取得対象として以下を検討した。

- 選択肢1: コミットのみ取得(シンプル)
- 選択肢2: コミットとPRの両方を取得し、集計で分けて扱う(学習重視)
- 選択肢3: PRのみ取得(成果単位重視)

## 決定

**選択肢2を採用する。** コミットとPRの両方を取得し、`github_activities` テーブルに
`type` カラム(`commit` / `pull_request`)で区別して同居させる。
二重カウントは「保存」ではなく「集計」の問題として扱い、集計時にコミットとPRを
別指標として分けて数えることで回避する(合算しない)。

### テーブル: github_activities

| カラム        | 型                          | NULL | 説明                                         |
| ------------- | --------------------------- | ---- | -------------------------------------------- |
| id            | 主キー(自動採番)            | 不可 | 内部ID                                       |
| type          | enum(commit / pull_request) | 不可 | 種別                                         |
| external_id   | 文字列                      | 不可 | コミットSHA or PR番号。一意キーの一部        |
| repository    | 文字列                      | 不可 | owner/repo 形式。一意キーの一部              |
| title         | 文字列                      | 不可 | コミットメッセージ or PRタイトル             |
| url           | 文字列                      | 不可 | 該当ページへのリンク(一覧表示用)             |
| activity_date | 日時                        | 可   | commit日時 or PRマージ日時。未マージPRはNULL |
| created_at    | 日時                        | 不可 | DBへ保存した日時                             |

- 一意制約: `(type, repository, external_id)` の3点で一意
- カラム名 `activity_date` は汎用名とし、中身(何の日時か)はソースごとに定義する

## 理由

1. **学習目的との整合**
   GitHub APIの2種類のエンドポイント(コミット/PR)を扱い、二重カウントを避ける
   集計設計を経験できる。実用と学習の両目的に資する。

2. **二重カウントは集計側で回避可能**
   ADR-0001で「明細は保存、集計は表示時に計算」と決めており、明細を両方持っても
   集計時にコミット数とPR数を別指標として扱えば合算による二重計上は起きない。

3. **一意キーを3点にした理由**
   PR番号はリポジトリ単位で採番されるため、`external_id` 単独や `(type, external_id)`
   では別リポジトリの同番号PRと衝突しうる。`repository` を含めて一意性を担保する。
   コミットSHAは全体で一意だが、ルール統一のため同じ3点セットを適用する。

4. **PRの代表日時にマージ日時を採用した理由**
   「完了した成果」を可視化する意図に合致する。作成日時ではなくマージ日時を
   `activity_date` に入れる。

## 未マージPRの扱い

- 未マージのPR(マージ日時が存在しない)は `activity_date` を NULL として保存する。
- データとしては保持するが、集計(推移グラフ・件数)では NULL のレコードを対象外とする。
- 一覧表示での見せ方(進行中として別枠表示 or 非表示)は実装フェーズで詳細化する。

## 検討した代替案

- **選択肢1(コミットのみ)**: MVPをシンプルにできるが、PRという成果のまとまりの観点が
  得られず、学習範囲も狭い。将来PRを足せる余地は残るが今回は不採用。
- **選択肢3(PRのみ)**: 成果単位で語りやすいが、日々の作業量(コミット)が見えない。不採用。

## 影響

- コミットとPRを合算した「総活動数」のような指標を出す場合は、二重カウントに注意し、
  原則として指標を分けて表示する。
- 集計クエリは `activity_date IS NOT NULL` を基本条件に含める。
- 同期処理は一意キー `(type, repository, external_id)` を用いて取り込み済み判定を行う。
