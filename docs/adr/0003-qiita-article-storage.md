# ADR-0003: Qiita記事は最新値のみを保持し(スナップショット履歴は持たない)、同期時にupsertする

- ステータス: 承認
- 日付: 2026-07-20
- 関連要件: F-02(Qiita連携), F-03(オンデマンド同期), F-11(活動の一覧表示)
- 関連ADR: ADR-0001(明細を保存し集計は参照時に行う)

## 背景

Qiita記事のデータをDBにどう保存するかを決める必要があった。
GitHubの活動データ(コミット/PR)と異なり、Qiitaのいいね数・ストック数・PV数は
時間とともに変動する(可変)値である。この「変動する値」をどう扱うかが論点。

保存方針として以下を検討した。

- パターンA: 記事マスタ + スナップショット履歴の2テーブル構成。
  同期のたびに指標を1行追加していき、いいね数やPV数の「推移」を追えるようにする。
- パターンB: 1記事1レコードで最新値のみを保持。同期のたびに上書きする。推移は追わない。

## 決定

**パターンBを採用する。** Qiita記事は `qiita_articles` テーブルに1記事1レコードで保存し、
いいね数・ストック数・PV数は同期のたびに最新値で上書きする。指標の推移(履歴)は保持しない。
同期処理は記事IDをキーとした upsert(存在すれば更新、なければ挿入)で行う。

また、PV数(page_views_count)も取得対象に含める。PV数は記事一覧APIには含まれず、
記事IDごとの個別APIコールが必要になる点を許容する。

### テーブル: qiita_articles

| カラム           | 型               | NULL | 説明                                             |
| ---------------- | ---------------- | ---- | ------------------------------------------------ |
| id               | 主キー(自動採番) | 不可 | 内部ID                                           |
| external_id      | 文字列           | 不可 | Qiita記事ID。一意キー                            |
| title            | 文字列           | 不可 | 記事タイトル                                     |
| url              | 文字列           | 不可 | 記事URL(一覧表示用)                              |
| activity_date    | 日時             | 不可 | 記事の投稿日時(created_at)。集計・並び替えの軸   |
| likes_count      | 整数             | 不可 | いいね数(同期時に上書き)                         |
| stocks_count     | 整数             | 不可 | ストック数(同期時に上書き)                       |
| page_views_count | 整数             | 可   | PV数(個別API取得。失敗時はNULL)                  |
| synced_at        | 日時             | 不可 | 最後にQiitaから取得した日時(指標の鮮度を示す)    |
| created_at       | 日時             | 不可 | DBへ保存した日時(自動)                           |
| updated_at       | 日時             | 不可 | レコード更新日時(Prismaの @updatedAt で自動管理) |

- 一意キー: `external_id`(Qiita全体で一意なため単独で可)
- `activity_date` はソース横断の共通カラム名。Qiitaでは投稿日時が入る。
- 日時カラムの役割: `created_at`(作成)/`updated_at`(レコード更新)/`synced_at`(API取得の鮮度)を区別する。詳細は設計書の共通設計方針を参照。

## 理由

1. **ツールの主目的との整合**
   本ツールの主目的は「自分がどれだけ取り組んだか(アウトプット量)」の可視化であり、
   いいね数やPV数(他者の反応)の推移は主目的から外れる。記事本数の推移は
   activity_date から算出でき、指標の履歴までは必須でない。

2. **MVPのシンプルさ**
   スナップショット履歴(パターンA)は履歴テーブルの設計・肥大化対策・集計の複雑化を伴う。
   最新値のみ(パターンB)なら実装が単純で、MVPに適する。

3. **synced_at で鮮度を担保**
   最新値のみ保持だと「その数値がいつ時点か」が失われるため、synced_at を持たせて
   「最後にQiitaから取得した時点の値」であることを明示する。
   なお synced_at(API取得の鮮度)は updated_at(レコード更新日時)とは意味が異なるため
   両方を別カラムとして持つ(同期を実行しても値が変わらなければ updated_at は動かないが、
   synced_at は更新したいケースがあるため)。

## 検討した代替案

- **パターンA(スナップショット履歴)**: いいね数・PV数の推移が見られ、履歴テーブル設計の
  学習価値もある。ただし主目的から外れ、MVPには過剰と判断し不採用。
  記事マスタ部分は共通のため、将来必要になれば履歴テーブルを追加して移行できる。

## タグの扱い

- Qiita記事のタグ(Python, Docker 等)は取得可能だが、1記事に複数付くため厳密には
  別テーブル(多対多)が必要になる。MVPでは複雑化を避けてタグを保持しない。
- 将来「どの技術をよくアウトプットしているか」を分析したくなれば、後から追加する。

## 影響

- 同期処理は「追加のみ」のGitHub(ADR-0002)と異なり upsert が必要。実装差異に注意。
- PV数取得のため記事数ぶんの個別APIコールが発生する。Qiita APIのレート制限
  (認証ありで概ね1時間あたり上限あり)を考慮し、ページング・スリープ等で配慮する。
- いいね数/PV数の推移分析は将来課題(パターンAへの拡張)として残す。
