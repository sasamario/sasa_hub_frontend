# ADR-0004: 同期処理は差分取得・リポジトリ単位トランザクション・失敗時継続で行う

- ステータス: 承認
- 日付: 2026-07-20
- 関連要件: F-01(GitHub連携), F-02(Qiita連携), F-03(オンデマンド同期)
- 関連ADR: ADR-0002(GitHubのコミット/PR), ADR-0003(Qiitaのupsert)

## 背景

オンデマンド同期(画面表示時 or 同期ボタン押下時にAPIを叩いてDBへ蓄積)の
具体的な処理方式を決める必要があった。論点は、差分取得の方法、同期状態の記録、
トランザクション境界、エラー時の振る舞い、Qiitaのレート制限対応。

## 決定

### 1. GitHubは前回同期日時を起点に差分取得する

- GitHubのコミット/PRは一度取得すれば変化しない(イミュータブル)。
  毎回全件を取り直すのは非効率なため、前回同期以降の分だけを取得する。
- 「前回同期日時」は sync_logs テーブル(下記)から取得する。

### 2. 差分取得の起点は finished_at ではなく started_at を用いる

- 同期処理には時間がかかり、その実行中にも新しいコミットが発生しうる。
  完了時刻(finished_at)を次回の起点にすると、実行中に発生した活動を
  取りこぼす可能性がある。
- 開始時刻(started_at)を起点にすれば、多少の重複取得は起こりうるが取りこぼしは防げる。
- 重複は一意キー `(type, repository, external_id)`(ADR-0002)で排除できる。
- 「取りこぼしは検知できないが、重複は後から消せる/弾ける」ため、安全側に倒す。

### 3. 同期状態は sync_logs テーブルに追加方式で記録する

同期を実行するたびに1レコードを追加(INSERT)していく。既存レコードの上書きはしない。

| カラム      | 説明                                           |
| ----------- | ---------------------------------------------- |
| id          | 主キー                                         |
| source      | github / qiita                                 |
| repository  | GitHubの場合の対象リポジトリ名。Qiitaでは NULL |
| status      | success / failed                               |
| started_at  | 同期開始日時(差分取得の起点として使用)         |
| finished_at | 同期完了日時                                   |
| message     | エラー内容など(任意)                           |

- GitHubはリポジトリ単位でログを記録する(source=github, repository=リポジトリ名)。
  リポジトリごとにテーブルを分けるのではなく、repository カラムで区別する。
- Qiitaは対象分割単位がないため1レコードで記録する(repository=NULL)。
- 差分取得の起点 = 対象の source(+repository)で status=success の最新レコードの started_at。
  failed のレコードは起点に使わない(失敗時に取りこぼした期間を再取得できるようにするため)。
- 追加方式のため履歴が残り、いつ失敗し・いつ復旧したかを後から追跡できる
  (将来的に同期ログ閲覧画面を設ける余地もある)。

### 4. GitHubはリポジトリ単位でトランザクションを貼る

- 1リポジトリの取り込みを1トランザクションとする。
- 取り込み中にエラーが発生した場合、そのリポジトリ分はロールバックし failed で記録する。
- 他のリポジトリは独立したトランザクションのため影響を受けず、成功分は確定する。
- 失敗したリポジトリは次回同期で前回成功時点(未成功なら初回)から取り直す。

### 5. エラー時は「続ける」(一部失敗しても全体を止めない)

- GitHub: あるリポジトリが失敗しても、残りのリポジトリの同期は継続する。
- Qiita: GitHubの同期が一部失敗しても、Qiitaの同期は実行する。
- 一部失敗が全体を巻き戻さないことで、「取れるものは取り、失敗分だけ次回リトライ」を実現する。

### 6. Qiitaは毎回全記事を取得して upsert し、レート制限対応は最小限とする

- Qiitaはいいね数・PV数など可変値を最新化する必要があり(ADR-0003)、差分取得では
  不十分なため、毎回全記事を対象に upsert する。
- PV数は記事ごとの個別APIコールが必要。対象は約70記事程度で今後大きく増える想定はなく、
  Qiita APIのレート制限(認証ありで概ね1000回/時)に対し十分余裕がある。
- よって予防的な待機(スリープ)は入れない。レート制限エラーが返った場合はそこで打ち切り、
  failed として記録し、次回同期でやり直す。

## 検討した代替案

- **全件取得+一意キーで重複排除(差分取得しない)**: 確実だがコミット増加に伴い毎回の
  取得・照合が増える。GitHubデータは不変のため差分取得で十分と判断し不採用。
- **同期状態を最新のみ上書き保持**: 差分取得の起点は取れるが履歴が残らず、失敗・復旧の
  追跡や将来のログ閲覧ができない。追加方式を採用。
- **エラー時に同期全体を中断**: 一部の失敗で他が更新されないのは個人ツールとして不便。
  「続ける」を採用。

## 影響

- 差分取得の起点計算は sync_logs への依存が生じる。起点が取れない(初回)場合の
  取得範囲(どこまで遡るか)は実装時に定める。
- started_at 起点による軽微な重複取得が発生しうるが、一意キーで吸収される。
- sync_logs はレコードが増加し続けるが、利用規模(手動同期・少数リポジトリ)では
  問題にならない。肥大化が問題化すれば古いログの定期削除を検討する。
