## 3. 共通設計方針

### 3.1 データ設計の基本原則

- **生データ(明細)を保存し、集計は参照時に行う。**
  事前に集計した値は基本的に保存せず、ダッシュボード表示時にクエリで算出する。
  これにより任意の切り口(月別・週別・種別別など)で後から集計でき、
  同期時の重複防止も一意キーで素直に実装できる。(ADR-0001)

### 3.2 ソース別テーブル方針

- 活動データはソース(GitHub / Qiita / 手動記録)ごとにテーブルを分ける。
  各ソースは持つ属性が異なるため、無理に単一テーブルへ統合しない。
- ダッシュボードでの集計・表示時に各テーブルを統合して扱う。

### 3.3 共通カラム: 日時の役割分担

全テーブルで日時カラムの意味を統一する。

| カラム | 意味 | 管理方法 | 対象 |
|---|---|---|---|
| `activity_date` | その活動が行われた日時。集計・並び替えの軸 | 各ソースから取得しセット | 活動系テーブル共通 |
| `created_at` | レコードをDBに初めて保存した日時 | Prisma `@default(now())` で自動 | 全テーブル |
| `updated_at` | レコードが最後に更新された日時 | Prisma `@updatedAt` で自動 | 全テーブル |
| `synced_at` | 外部APIから最後にデータを取得した日時(データの鮮度) | 同期処理で明示的にセット | API連携テーブルのみ |

補足:
- `activity_date` はソース横断の共通名とし、中身(何の日時か)はソースごとに定義する。
  - GitHub(commit): コミット日時 / GitHub(PR): マージ日時 / Qiita: 投稿日時
- `updated_at` と `synced_at` は意味が異なる。同期を実行しても取得値が前回と同じ場合、
  レコードは変化しないため `updated_at` は動かないが、`synced_at` は更新したい。
  よって両者を別カラムとして持つ。

## 4. データモデル(確定分)

### 4.1 github_activities(GitHub活動)

コミットとPRの両方を1テーブルに `type` で区別して保存する。
明細を保存し、コミット数・PR数などは集計時に算出する。(ADR-0002)

| カラム | 型 | NULL | 説明 |
|---|---|---|---|
| id | 主キー(自動採番) | 不可 | 内部ID |
| type | enum(commit / pull_request) | 不可 | 種別 |
| external_id | 文字列 | 不可 | コミットSHA or PR番号。一意キーの一部 |
| repository | 文字列 | 不可 | owner/repo 形式。一意キーの一部 |
| title | 文字列 | 不可 | コミットメッセージ or PRタイトル |
| url | 文字列 | 不可 | 該当ページへのリンク(一覧表示用) |
| activity_date | 日時 | 可 | commit日時 or PRマージ日時。未マージPRはNULL |
| created_at | 日時 | 不可 | DB保存日時(自動) |
| updated_at | 日時 | 不可 | レコード更新日時(自動) |

- 一意制約: `(type, repository, external_id)` の3点で一意
- 同期は「追加のみ」。一意キーで取り込み済みを判定して重複を防ぐ。
- 未マージPR(activity_date = NULL)はデータとして保持するが、集計対象からは除外する。
  一覧表示での見せ方は実装フェーズで詳細化する。
- コミット数とPR数は別指標として扱い、単純合算による二重カウントを避ける。

### 4.2 qiita_articles(Qiita記事)

1記事1レコードで最新値のみ保持する。同期のたびに upsert(存在すれば更新・
なければ挿入)で最新のいいね数・PV数等に上書きする。推移(履歴)は保持しない。(ADR-0003)

| カラム | 型 | NULL | 説明 |
|---|---|---|---|
| id | 主キー(自動採番) | 不可 | 内部ID |
| external_id | 文字列 | 不可 | Qiita記事ID。一意キー |
| title | 文字列 | 不可 | 記事タイトル |
| url | 文字列 | 不可 | 記事URL(一覧表示用) |
| activity_date | 日時 | 不可 | 記事の投稿日時(created_at)。集計・並び替えの軸 |
| likes_count | 整数 | 不可 | いいね数(同期時に上書き) |
| stocks_count | 整数 | 不可 | ストック数(同期時に上書き) |
| page_views_count | 整数 | 可 | PV数(記事ごとの個別API取得。失敗時はNULL) |
| synced_at | 日時 | 不可 | 最後にQiitaから取得した日時(鮮度) |
| created_at | 日時 | 不可 | DB保存日時(自動) |
| updated_at | 日時 | 不可 | レコード更新日時(自動) |

- 一意キー: `external_id`(Qiita全体で一意なため単独で可)
- 同期は upsert。GitHub(追加のみ)と実装が異なる点に注意。
- PV数は記事一覧APIに含まれず、記事IDごとの個別APIコールが必要。
  Qiita APIのレート制限に配慮する(ページング・スリープ等)。
- タグはMVPでは保持しない(将来、多対多で追加可能)。

### 4.3 保留中のテーブル

| テーブル | 用途 | 状態 |
|---|---|---|
| manual_records | 手動記録(資格・書籍・勉強会など) | 方針未定。カテゴリの持ち方などを後日検討 |
| sync_logs | 同期ログ(いつ同期したか) | 任意。必要性を含め後日検討 |

## 5. 画面設計(確定分)

### 5.1 共通レイアウト

全画面で共通の外枠を持つ。左サイドメニュー + 右メインエリアの2カラム構成。
サイドメニューは固定で、メインエリアのみ画面ごとに切り替わる。
Nuxtのレイアウト機能で共通化する。

- サイドメニュー項目: ダッシュボード / GitHub詳細(Qiita詳細は実装時に追加)
- 現在表示中の画面をハイライトする。

### 5.2 ダッシュボード画面

全ソース横断のサマリーを表示するトップ画面。表示内容は選択期間に連動する。

構成(上から):

1. **期間セレクタ + 同期ボタン**
   - 期間プリセット(直近1年 / 6ヶ月 / 3ヶ月 / 任意期間)。デフォルトは直近1年。
   - 同期ボタンでオンデマンド同期を実行する。
   - 画面内の数値・グラフはすべて選択期間に連動する(ラベルも期間に応じて変わる)。
2. **サマリーカード(ソース別)** — カードクリックで各詳細画面へ遷移。
   - GitHubカード: コミット総数、PR総数
   - Qiitaカード: 記事数、合計view数、合計LGTM数
3. **コミット推移グラフ**
   - 週別固定の折れ線グラフ。
   - リポジトリ選択式(デフォルト「すべて(合計)」、個別リポジトリに切替可)。
4. **リポジトリ別コミット数の割合(円グラフ)**

### 5.3 GitHub詳細画面

GitHubに絞って掘り下げる画面。ダッシュボードが「要約」なのに対し
「粒度自由・一覧あり」で詳細を確認する。

構成(上から):

1. **画面見出し + 期間セレクタ**
2. **コミット推移グラフ**
   - 粒度切り替え(日別 / 週別 / 月別)。ダッシュボード(週別固定)の上位互換。
   - リポジトリ選択式(デフォルト「すべて(合計)」)。
3. **活動一覧**
   - 全リポジトリのコミット/PRを時系列でフラットに表示(案A)。
   - フィルタ: リポジトリ絞り込み / 種別絞り込み(コミット・PR)。
   - 1行の項目: 日付 / 種別バッジ(commit・PR番号) / リポジトリ名 / タイトル / 外部リンク。
   - 行クリックでGitHubの該当ページを開く。
   - 「さらに読み込む」方式で追加読み込み(ページングではない)。

### 5.4 保留中の画面

|---|---|
| Qiita詳細画面 | 今回のMVPスコープ外。おいおい設計する |
| 手動記録の登録・一覧画面 | 手動記録の方針未定のため保留 |

## 6. REST API設計(確定分)

### 6.1 設計方針

- **リソース単位でエンドポイントを分ける(REST的)。** 画面単位でまとめる(BFF的)方式は採らない。
  - 1画面の中に独立して動く領域が存在するため(例: ダッシュボードのリポジトリ切替は
    折れ線グラフのみ、GitHub詳細の粒度トグルはグラフのみ、一覧フィルタは一覧のみを更新)。
  - 同じ集計を複数画面で再利用できる(推移グラフはダッシュボードとGitHub詳細で共用)。
  - ローカル実行のためリクエスト回数増加のコストは実質無視できる。
- **URL構造は `/api/{ソース}/{対象}` とする。** `stats` のような接頭辞は冗長なため付けない。
  URLを見れば何のデータか分かることを優先する(例: `/api/github/commits/timeseries`)。

### 6.2 エンドポイント一覧

| メソッド | パス | 用途 | 主なパラメータ |
|---|---|---|---|
| GET | `/api/github/commits/timeseries` | コミット推移(折れ線グラフ) | from, to, unit(day/week/month), repository |
| GET | `/api/github/commits/by-repository` | リポジトリ別コミット数(円グラフ) | from, to |
| GET | `/api/github/summary` | GitHubサマリーカード(コミット総数・PR総数) | from, to |
| GET | `/api/qiita/summary` | Qiitaサマリーカード(記事数・view合計・LGTM合計) | from, to |
| GET | `/api/github/activities` | 活動一覧(コミット/PR明細) | from, to, repository, type, limit, cursor |
| POST | `/api/sync` | 全ソース一括同期 | - |
| POST | `/api/sync/github` | GitHubのみ同期 | - |
| POST | `/api/sync/qiita` | Qiitaのみ同期 | - |

補足:

- **推移グラフAPIは両画面で共用する。** ダッシュボードは `unit=week` 固定で呼び、
  GitHub詳細は粒度トグルに応じて `unit` を切り替える。
  `repository` 未指定時は全リポジトリの合計を返す。
- **同期APIは一括とソース別の両方を用意する。** 画面の同期ボタンは一括を使い、
  ソース別は開発時や個別再取得に用いる。
- **リポジトリ一覧の専用エンドポイントは設けない。**(6.4参照)

### 6.3 活動一覧のページング(カーソル方式)

活動一覧は `limit`/`offset` ではなく**カーソル方式**を採用する。

- レスポンスに次の取得開始位置を示す `nextCursor` を含める。
  クライアントは次リクエストで `cursor` として渡す。
- 最終ページでは `nextCursor` を null とし、「さらに読み込む」ボタンを非表示にする。
- カーソルは並び順の基準値である `activity_date` と、同値の場合に備えた `id` を
  組み合わせて位置を一意に特定する。
- 本一覧は `activity_date IS NOT NULL` を条件に含める
  (未マージPRは並び順を決められないため一覧・集計から除外する。ADR-0002準拠)。

イメージ:

```
GET /api/github/activities?limit=20
→ { items: [...20件...], nextCursor: "2026-07-15T10:30:00Z_123" }

GET /api/github/activities?limit=20&cursor=2026-07-15T10:30:00Z_123
→ { items: [...次の20件...], nextCursor: null }
```

### 6.4 対象リポジトリの扱い

- **追跡対象のリポジトリは設定(環境変数・設定ファイル)で明示的に定義する。**
  この定義が「同期時に取得する対象」と「画面の選択肢・凡例の母集団」を兼ねる。
- `/api/github/commits/by-repository` は、**期間内に活動がないリポジトリも count 0 で返す**。
  これにより円グラフの凡例に0%として表示でき、推移グラフ・一覧フィルタの
  リポジトリ選択肢もこのレスポンスから生成できる。
- 上記により、リポジトリ一覧専用のエンドポイントは不要とする。
- 将来、画面からリポジトリを追加・削除したくなった場合は、設定ではなく
  DBテーブル(例: tracked_repositories)で保持する形へ発展させる。
