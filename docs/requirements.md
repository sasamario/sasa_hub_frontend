# 要件定義書: 自己学習可視化ツール(仮称)

- 版: 初版
- 作成日: 2026-07-20
- ステータス: 要件定義完了

---

## 1. 背景・目的

### 背景

日々自己学習に取り組んでいるが、何をどのくらい取り組んだかを示す定量的な記録が存在しない。

### 目的

1. **実用目的**: 自己学習の成果物を継続的に記録・可視化し、「何をどのくらい取り組んだか」を定量的に振り返れる状態にする
2. **学習目的**: AIを活用してフロントエンド・バックエンドを一から開発し、理解を深めたい技術の習得を兼ねる

### 成功の定義(ゴール)

- 普段の活動(GitHub・技術記事)を簡単な操作でデータとして蓄積できる
- APIで取れない活動(資格・書籍など)を手軽に手動登録できる
- ダッシュボードを開けば、指定期間の活動量・内訳が一目で分かる

## 2. 利用者・利用環境

| 項目     | 内容                                             |
| -------- | ------------------------------------------------ |
| 利用者   | 本人のみ(シングルユーザー)                       |
| 利用端末 | PCブラウザ中心                                   |
| 動作環境 | ローカルPCで動作すれば十分(外部公開・認証は不要) |
| 利用頻度 | 手動登録: 随時 / 振り返り: 月次程度+必要時       |

## 3. ユースケース

### UC1: 活動データの同期(オンデマンド)

システムを開いたとき、または同期ボタンを押したタイミングで、外部API(GitHub・Qiita)から活動データを取得し、DBに蓄積する。cron等による定期実行は行わない。

### UC2: 日常の記録(手動)

資格取得、書籍の読了、勉強会参加など、APIで取得できない成果物をフォームから登録する。

### UC3: 振り返り

ダッシュボードで期間(例: 直近6ヶ月)を指定し、活動の量・内訳・推移をグラフと一覧で確認する。

## 5. 非機能要件

| 分類         | 要件                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| 対応ブラウザ | PCのモダンブラウザ(Chrome想定)。レスポンシブ対応は必須としない                                                   |
| 性能         | 個人利用のため厳しい要件なし。ダッシュボード表示は数秒以内目安。同期処理中はローディング表示等で状態が分かること |
| セキュリティ | 外部APIトークンをコードに直書きしない(環境変数等で管理)。リポジトリにトークンをコミットしない                    |
| データ保全   | DBのデータが消えないこと(最低限のバックアップ手段を用意)                                                         |
| 運用         | 個人がメンテナンスできるシンプルな構成であること                                                                 |
| コスト       | 無料で運用できること(ローカル完結)                                                                               |

## 6. MVPスコープ

**MVP = 「Must」の機能のみ**

1. GitHub連携でコミット/PRをオンデマンド同期(同期ボタン)で取り込める
2. 手動記録の登録・編集・削除ができる
3. ダッシュボードで期間指定し、推移グラフ・カテゴリ内訳・一覧が見られる

Qiita連携・設定画面・自動取り込み(検討要件)などは MVP後の拡張(v2以降)とする。

## 7. 技術選定

学習目的(理解を深めたい技術の習得)を主軸に選定。

| 領域                   | 技術                | 状態 |
| ---------------------- | ------------------- | ---- |
| フロントエンド         | TypeScript / Nuxt 4 | 決定 |
| バックエンド           | TypeScript / NestJS | 決定 |
| データベース           | PostgreSQL          | 決定 |
| ORM                    | Prisma              | 決定 |
| フロント・バック間連携 | REST API            | 決定 |
| 開発環境               | Docker              | 決定 |
| 実行環境               | ローカルPC          | 決定 |

### 選定理由の補足

**Nuxtのバージョン(v3ではなくv4を採用)**

- 当初は業務で利用しているNuxt 3の知見を深める目的でv3を候補としていた
- ただし、Nuxt 3は2026年7月末にEOL(サポート終了)を迎え、新規開発でこれから採用する合理性が低い
- Nuxt 4はv3の作り直しではなく進化版であり、コンポーネント記法・composables・自動インポート等の中核は共通。v4で開発してもv3の知見はそのまま深まる
- 主な差分はディレクトリ構造(`app/`配下への集約)とTypeScript型管理の厳密化(app/server/sharedのコンテキスト分離)であり、後者はTypeScript学習の目的にも合致する
- 業務側も将来的にv4移行が見込まれるため、先行して差分・移行の勘所を習得できるメリットがある

**その他**

- フロント・バックをTypeScriptに統一することで、型システムを1言語で深く学ぶ
- Nuxtにもサーバー機能(Nitro)はあるが、バックエンド開発の学習を目的としてNestJSを別途構築する構成をあえて採用する
- ORMはPrismaを採用。型安全性・マイグレーション体験・学習リソースの豊富さに優れ、個人開発でのMVP完成を優先する判断
