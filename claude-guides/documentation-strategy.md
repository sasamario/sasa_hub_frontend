# ドキュメント設計の考え方

> このガイドは開発全般で役立つ汎用知識です。他の開発でも参考にできます。

## なぜドキュメントを分けるのか

すべてを1つの巨大なファイルに書くと、「今の正しい仕様」も「なぜそうしたかの経緯」も
「作業手順」も混ざり、読みにくく・探しにくくなる。
**役割の違うものは別のファイルに分ける** ことで、それぞれが読みやすく保守しやすくなる。

## ドキュメントの役割分担(例)

このプロジェクトで採用した構成。汎用的に流用できる。

| ドキュメント    | 役割                               | 性質       |
| --------------- | ---------------------------------- | ---------- |
| requirements.md | 何を作るか(要件)                   | 決めたこと |
| architecture.md | どう作るか(設計のスナップショット) | 現在の正解 |
| adr/            | なぜそう決めたか(判断の記録)       | 経緯・履歴 |
| docs/guides/    | どう作業するか(手順書)             | 再現手順   |
| tasks.md        | 何が残っているか(進行表)           | 進捗       |

ポイントは **「現在の正解(architecture.md)」と「判断の経緯(ADR)」を分ける** こと。
設計書に経緯まで全部書くと「結局どういう設計?」が読み取りにくくなる。
経緯は ADR に逃がし、設計書は今の姿だけを簡潔に保つ。

## ADR とは

**Architecture Decision Record(設計判断の記録)**。
「なぜこの選択をし、どの代替案を却下したか」を1決定=1ファイルで残す軽量な手法。

### なぜ有用か

後から「なぜこうしたんだっけ?」と自分の判断を疑う無限ループを防げる。
却下した案とその理由が残っていれば、「その案は前に検討して、こういう理由でやめた」と
すぐ思い出せる。

### 典型的な構成

- ステータス(承認 / 非推奨 など)
- 背景(何を決める必要があったか)
- 決定(何を選んだか)
- 理由
- 検討した代替案(却下したものとその理由)← これが特に重要
- 影響

### 運用ルール

- **基本的に後から書き換えない。** 決定を覆すときは、そのADRのステータスを「非推奨」に変え、
  新しいADRを起こす。判断の履歴そのものが資産になる。
- **番号は連番** にし、ファイル名の先頭に付ける(例: `0001-...md`)。時系列で並ぶ。

## 手順書(guides)の役割

「テーブルを追加するには、このファイルを用意してこのコマンドを実行する」のような
**再現可能な作業手順** を残す場所。初めてやった作業を手順化しておくと、
次回同じ作業を迷わず・調べ直さずにできる。

- 作業の種類ごとにファイルを分ける。
- 「用意するもの」「実行するコマンド」「注意点」を具体的に書く。

## 汎用知識は別の場所に分ける

「このプロジェクトの設計」と「ツールの使い方など他プロジェクトでも使える知識」は
性質が違う。混ぜず、別のフォルダ(このプロジェクトでは `claude-guides/`)に分けると、
後で他のプロジェクトへ持ち出しやすい。
